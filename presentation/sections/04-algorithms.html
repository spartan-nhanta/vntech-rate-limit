4.4 · Token bucket · how each request decides

No timer refills the bucket; each request does the math

capacity = 5 tokens · rate = 5 tokens / s · each request spends 1 token
  • fractional Tokens can be fractional. 0.1 s × 5 tokens/s = 0.5 token. A request needs at least 1.
  • no refill job Nothing tops up the bucket on a timer. Each request computes tokens = min(5, tokens + elapsed × 5).
  • 429 Fewer than 1 token → reject. Retry-After = (1 − tokens) / rate, so the client knows exactly when a token will be there.

4.5 · Leaky bucket

Requests pour in at any speed. The hole at the bottom lets out 5 per second.

capacity = 5 requests · rate = 5 requests / s
  • use case Application layer, right before calling a 3rd-party API.
  • Users send 10 SMS within one second. The SMS gateway accepts only 5 per second.
  • The bucket holds the burst and lets out 5 per second. The vendor never sees a spike, so it never sends us a 429.

Token bucket vs. leaky bucket

Same algorithm, opposite state variable

token bucket · counts what's left
tokens = min(capacity,
         tokens + elapsed × refill_rate)
if tokens < 1: reject
tokens -= 1
leaky bucket · counts what's used
water = max(0,
        water - elapsed × leak_rate)
if water + 1 > capacity: reject
water += 1
  • naming Token bucket speaks of tokens and a refill_rate; leaky bucket of water (or queue size) and a leak_rate.
  • formula One adds and clamps at the top, the other subtracts and clamps at zero. At every moment tokens = capacity − water.
  • same decisions Given the same capacity and rate, the counter versions allow and reject exactly the same requests.
  • where they differ Leaky bucket as a real queue delays requests instead of rejecting them — that's what makes output smooth.
