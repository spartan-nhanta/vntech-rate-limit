3.2 · Race & fix

GET then SET from two pods lets both requests through. One Lua script fixes it.

Race · GET and SET are two round trips
# tokens left = 1
Pod A  GET tokens   → 1
Pod B  GET tokens   → 1   # both see 1
Pod A  SET tokens 0 → allow
Pod B  SET tokens 0 → allow  should be 429

Both pods read before either writes. One request slips through.

Fix · read + decide + write in one script
-- Redis runs the whole script,
-- nothing runs in between
local t = tonumber(redis.call('GET', KEYS[1]))
          or tonumber(ARGV[1])  -- capacity
if t >= 1 then
  redis.call('SET', KEYS[1], t - 1)
  return 1  -- allow
end
return 0    -- 429

Pod B's script waits for Pod A's, reads 0, and returns 429.

3.3 · Redis Cluster

A Lua script only runs on one node

# no hash tag — the two keys can land
# on two different nodes
rl:user_456:prev  → node A
rl:user_456:curr  → node B  CROSSSLOT

# hash tag {} — Redis hashes only
# the part inside the braces
rl:{user_456}:prev  → hash "user_456" → node B
rl:{user_456}:curr  → hash "user_456" → node B  same node

Two related keys on two different cluster nodes make the Lua script that needs both of them fail outright with a CROSSSLOT error. Wrapping the shared part of the key in {} tells Redis to hash only that substring, guaranteeing every key sharing it lands on the same node — and the script stays legal.
