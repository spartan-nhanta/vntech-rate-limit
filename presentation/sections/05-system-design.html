5.3 · Redis Cluster sharding

Per-user keys hash naturally; global keys don't

// per-user: one natural key, one node
rl:{user_456}:token
// hash "user_456" → 1 fixed slot → 1 fixed node
// Lua script stays legal, no CROSSSLOT

// global per-endpoint: no natural entity key,
// so split across N shards instead
rl:global:{/api/send}:shard:{random(0,15)}
// 16 shards, each budgeted at
// total_limit / 16 × 1.1   (10% buffer)

A per-user limit has a natural key and hashes to one node cleanly. A global, per-endpoint limit has no such entity — sharding it across 16 keys spreads the writes instead of hammering one hot key, trading a small amount of precision (the buffer) for throughput.

The buffer exists because 16 independently-checked shards can each individually allow a request right at their own edge, letting the true global total run slightly over — accepted on purpose.

5.4 · Hard limit vs. soft limit

Same check, a different response to the result

Hard limit
Crossing it rejects immediately

Free tier: 100 req/min, no exceptions. Behavior: an instant 429. Used for security and preventing abuse — there's no negotiating with it.

Soft limit
Crossing it warns, but keeps serving

Pro tier: 1,000 req/min — cross it and the request still goes through, logged and flagged for an overage charge rather than rejected. Business flexibility, not security.

val result = rateLimiter.check(userId)
when {
  result.count > hardLimit -> return HTTP_429
  result.count > softLimit -> { logger.warn("approaching limit"); proceed() }
  else -> proceed()
}

The same rateLimiter.check() call backs both — what differs is purely what the calling code does with the result.

5.5 · When Redis itself is down

Fail-open vs. fail-closed

Fail-open
Let every request through

Higher availability, briefly no protection. Most public APIs choose this, paired with a circuit breaker and tight monitoring — an outage in the limiter shouldn't take down the product it was protecting.

Fail-closed
Reject everything

Protects billing and security, drops availability to zero for the duration. Chosen when letting anything unmetered through is worse than an outage — payment and quota enforcement, mostly.

"Most public APIs fail open" is the practical default — the limiter existing to protect availability shouldn't itself become the single point of failure that removes it.

5.6 · Being a good client

Pace before the limit, absorb the 429 after

Retry-After
Read it, then re-enqueue

The response header names the wait, either as seconds or as an HTTP date. Clamp it to a sane range, then put the same job back on the queue with that delay.

Shared circuit gate
One 429 should speak for everyone

A single shared "closed until" timestamp means one rejected call pauses every concurrent request — instead of each one discovering the limit by being rejected in turn, which is the behavior most likely to get a whole integration blocked outright.

pacer draining evenly, ahead of the limit429 → gate closes for a bounded window

A token-bucket pacer and a reactive circuit gate solve different halves of the same problem: the pacer tries to never get a 429 in the first place, the gate makes sure one 429 isn't wasted as a signal only its own request sees.
