SECTION 1

Introduction

What rate limiting is, the two concepts people conflate with it, and how a client is told to back off.

Set up the vocabulary before any mechanism — this is the section that keeps "throttling" and "rate limiting" from being used as synonyms for the rest of the deck.

2 / 43act i · introduction
Three concepts, one confusion

Rate limiting, throttling, and load shedding aren't the same thing

ConceptBehavior once past the thresholdWhere it actually lives
Rate limitingReject immediately — 429HTTP API servers
ThrottlingDelay — hold the item, process it laterAsync workers, queue consumers
Load sheddingReject selectively when the whole system is overloadedCircuit breakers, infrastructure
  • AWS, Stripe, and GitHub all call their 429 behavior "rate limiting" even though, strictly, it's a reject — not a delay. In plain HTTP APIs the two words get used interchangeably.
  • Real throttling shows up in async systems: a worker pulling off a Kafka topic paces itself against a shared limiter before pushing to a downstream SMS gateway — it sleeps, it doesn't reject, and there's no HTTP client waiting on the other end.

Get this distinction settled early — every later slide about client behavior (backoff, retry, circuit gates) depends on knowing whether the caller is being rejected or merely delayed.

3 / 43rate limiting vs. throttling vs. load shedding
The vocabulary in HTTP

Three status codes that get confused

429 Too Many Requests   // rate limit — client sent too much
503 Service Unavailable // load shedding — server is overloaded
403 Forbidden           // authorization — NOT rate limiting

Retry-After: 30                // seconds to wait
X-RateLimit-Limit: 100         // the configured limit
X-RateLimit-Remaining: 0       // how much is left
X-RateLimit-Reset: 1704067320  // epoch time of the next reset
  • 429 is the caller's fault — they can fix it by slowing down.
  • 503 is the server's problem — retrying won't necessarily help until it recovers.
  • 403 means "no," permanently, regardless of rate — retrying is never the fix.

A surprising number of production incidents come from a client retrying a 403 as if it were a 429 — reading the code, not just the fact that something failed, matters.

7 / 43client-side · debounce, batch, backoff
Why jitter matters

1,000 clients, no jitter, waking in unison

Exponential backoff only spaces the retries further apart over time — it never makes concurrent clients diverge from each other. Jitter is the only ingredient that does that. Full jitter produces the lowest total load; equal jitter guarantees at least half the base delay.

8 / 43jitter · simulated, per AWS's "Exponential Backoff and Jitter"
Three jitter formulas

Equal jitter is the common middle ground

StyleWait time
Full jitterrandom(0, min(cap, base·2ⁿ))
Equal jittert/2 + random(0, t/2)
Decorrelatedmin(cap, random(base, prev·3))
 
base = min(previousDelay * multiplier, maxDelay)
return random(base / 2, base + 1)

One catch: if the next attempt's base is computed from the previous jittered delay rather than the original, each retry only grows by roughly 1.5× on average, not the intended 2×.

Full jitter produces the lowest aggregate load, per AWS's own writeup. Decorrelated jitter is attractive because it needs no retry counter at all — only the previous wait.

9 / 43jitter formulas
Retry-After still needs jitter

"Wait 60 seconds" — and everyone wakes at second 60

The header tells every caller the same number, so obeying it literally recreates the herd it was meant to prevent. Adding a small jitter on top — retryAfter + random(0, 20%) — is the cheapest fix.

2.2 · Infrastructure

One thread, ten thousand connections

Nginx isn't just a web server — it's a reverse proxy standing in front of the whole system, and this is the layer that stops a request before it ever reaches application code.

Most traditional web servers use thread-per-connection: 10,000 connections means 10,000 threads — expensive in memory, slow to context-switch.

Event-driven, non-blocking I/O
One worker, thousands of connections

A single event loop thread reacts to data ready, response ready, new connection, timeout — while waiting on network I/O, the worker does other work instead of blocking on it. The same idea as Node.js's event loop, in C, and faster.

This is why Nginx can front 10K concurrent connections on a single core — it isn't magic, it's just never blocking a thread on I/O it could be doing something else during.

11 / 43nginx · event loop
2.2 · Infrastructure

Nginx enforces rate limits as a leaky bucket

# declare a zone: by IP, 10MB, 10 req/s
limit_req_zone $binary_remote_addr
  zone=api:10m rate=10r/s;

server {
  location /api/ {
    limit_req zone=api burst=20 nodelay;
    # burst=20 : queue up to 20 requests over rate
# nodelay  : reject past that, no delay
    proxy_pass http://backend;
  }
}
  • burst is the leaky bucket's queue size — this directive is a leaky bucket by another name.
  • load balancing round robin (default), least_conn, ip_hash (sticky sessions), or weight=N sit right alongside it in the same upstream block.
  • Kong / Envoy centralize the same idea as a plugin/config shared across every gateway node — no per-service code to write.

Infrastructure-layer limiting is coarse — it only knows the IP, never the user or their subscription tier. That gap is exactly what the application layer fills next.

2.3 · Application / middleware

Where business context lives that infrastructure can't see

val tier = userService.getTier(userId)
// free / pro / enterprise

val limit = when (tier) {
  "enterprise" -> 10_000
  "pro"        -> 1_000
  else         -> 100      // free
}

val result = rateLimiter.check(
  key = "$userId:$endpoint", limit = limit)
  • Tier-based limits — a VIP or paying customer gets a materially higher budget than a free account.
  • Per-endpoint limits — a slow /export gets its own, tighter budget than a cheap read.
  • Per-API-key, not per-IP — many users legitimately share one office IP; a key identifies the actual caller.

Infrastructure rate limiting is thick and coarse; application-layer limiting is where product decisions — who gets more, what costs more — actually get enforced.

Distributed state

Why Redis, why Lua — the foundation every algorithm in the next section is built on.

The multi-pod counter problem, the race it creates, the atomic fix, Redis Cluster's hash-tag requirement, and where precision trades off against performance.

14 / 43act iii · distributed state
3.1 · The problem

Every pod counting on its own adds up to nothing

Three replicas, three independent in-memory counters, three numbers each under budget — and a real total that isn't. The fix is a counter shared in Redis, not three local ones.

15 / 43distributed state · the problem
3.2–3.3 · Race & fix

Two commands, one race

Two round trips — not atomic
count = INCR(key)      // (1)
if count == 1:
  EXPIRE(key, ttl)    // (2)
return count
  • Crash between (1) and (2): the key exists with no expiry at all.
  • The counter for that key now grows forever, and every future attempt gets blocked by a limit that never resets.
  • the fix Redis is single-threaded — a Lua script (EVAL/EVALSHA) runs to completion with nothing interleaved. Wrap the read-decide-write in one script and the second pod simply sees the already-updated value.

This is the sharpest edge in any counter-based limiter built on a key-value store: two commands that look sequential in the code are two separate round trips to the server, and anything can happen in between them.

16 / 43atomicity · Lua scripts
3.4 · Redis Cluster

A Lua script only runs on one node

# no hash tag — the two keys can land
# on two different nodes
rl:user_456:prev  → node A
rl:user_456:curr  → node B  CROSSSLOT

# hash tag {} — Redis hashes only
# the part inside the braces
rl:{user_456}:prev  → hash "user_456" → node B
rl:{user_456}:curr  → hash "user_456" → node B  same node

Two related keys on two different cluster nodes make the Lua script that needs both of them fail outright with a CROSSSLOT error. Wrapping the shared part of the key in {} tells Redis to hash only that substring, guaranteeing every key sharing it lands on the same node — and the script stays legal.

This is a Redis Cluster-specific gotcha that doesn't show up at all against a single Redis instance — worth knowing before the first CROSSSLOT error in production.

SECTION 4

Algorithms

Six ways to decide whether a request gets through — all six assume the Redis + Lua foundation above.

Cheapest first: fixed window, sliding log, sliding counter, token bucket, leaky bucket, then GCRA as the one-field rewrite of token bucket.

19 / 43act iv · algorithms
4.4 · Token bucket

A burst, then a steady drip

called immediatelysleeping off its debt
  • lazy refill No background thread tops up the bucket. Each call computes tokens = min(capacity, tokens + elapsed × rate) on the spot.
  • borrow ahead When the bucket is empty, let the count go negative and sleep exactly the deficit — instead of parking every caller until the next refill and having them race each other.
  • bounded wait If the computed wait exceeds a cap, fail fast instead of queuing indefinitely — a busy caller should hear about it, not stall a batch job.

Allows controlled bursts, O(1), gives an exact Retry-After, no boundary spike — the generally recommended default. Needs two tuned parameters: capacity and rate.

20 / 43token bucket
Token bucket · mechanics

Borrow first, then sleep off the debt

function acquire():
  lock:
    refill()
    deficit = 1 - tokens
    wait = deficit <= 0 ? 0
         : ceil(deficit / rate * 1000)  // ms
    if wait > MAX_WAIT:
      raise RateLimitExceeded(wait)
    tokens -= 1  // reserved before sleeping, can go negative
  if wait > 0:
    sleep(wait)
  • Debit before sleeping. The next caller sees the bucket already negative and computes a longer wait of its own — no two callers ever land on the same wake-up moment.
  • The lock only covers the arithmetic, not the sleep. Reserving a token happens inside the critical section; sleeping happens outside it, so waiting callers never block each other.
  • The bounded-wait exception is the one signal that matters. A window that's genuinely oversubscribed should surface as a fast, explicit failure — not a batch job that quietly hangs.

This is how ten concurrent callers end up queued 200 ms apart instead of all waking on the same refill tick and stampeding for the same token.

21 / 43token bucket · pseudocode
4.5 · Leaky bucket

Smooth the output, not the input

  • Instead of enqueuing thousands of jobs at once, each one gets a delay proportional to its position in the queue: delay = index / jobsPerSecond.
  • A durable queue plays the role of the bucket, draining downstream at a constant, predictable rate no matter how bursty the enqueue was.
  • counter vs. queue A counter-based leaky bucket isn't a true smoother — it can still let a burst through if the queue has room. Genuinely smooth output needs a real FIFO queue, like a worker pulling off Kafka.

Leaky bucket is the traffic-shaping half of the pair — it protects whatever is downstream from ever seeing a spike, at the cost of some added latency for the items at the back of the queue.

22 / 43leaky bucket
4.1 · Fixed window counter

Cheap to run, leaky at the seams

  • the appeal One counter per key, reset on a timer. INCR + EXPIRE — doesn't even need Lua, since INCR is already atomic on its own.
  • boundary burst A caller who spends the limit at the end of window A and again at the start of window B gets roughly double the intended rate in a short span.
  • If the counter's TTL is set only on the first hit and never refreshed, the window is anchored to that caller's own history, not to a shared clock — which is what makes two windows able to abut like this.

This is the classic fixed-window failure mode: burst at the trailing edge of one window, burst again at the leading edge of the next, and the two combine into a spike the limit was never meant to allow.

24 / 43fixed window · common surfaces
Design details that matter

Picking the right key is most of the design

Compose the key
Never key on a value the caller supplies alone

A limiter keyed on "email" alone lets anyone lock a real user out by typing their address ten times. Pair the caller-supplied value with something the caller can't choose — their address, in this case.

Match the response
A rejection shouldn't leak information

On a login endpoint, returning the same error for "rate limited" and "wrong password" keeps an attacker from using the limiter itself to enumerate which accounts exist.

Trust the right hop
X-Forwarded-For is a list, not a value

A load balancer appends the real client address to the end of the header. Reading the first entry instead of the last lets a caller simply forge their way past the limiter.

All three of these are cheap to get right and expensive to get wrong — they don't change the algorithm, just whether the algorithm is actually enforcing what it looks like it's enforcing.

25 / 43fixed window · key design
4.2 · Sliding window log

Perfectly accurate, and it shows in the memory bill

  • A Redis sorted set per key: ZREMRANGEBYSCORE trims anything older than the window, ZCARD counts what's left, ZADD writes the new timestamp.
  • No boundary artifact at all — the window truly slides, so there's no clock edge to exploit.
  • The cost: memory per key scales with request volume, not with a constant. 100 req/min per user × 1M users = 100M sorted-set entries.

Sliding window log is the gold standard for accuracy and the worst choice for memory. It earns its keep only where correctness genuinely outweighs the cost — billing is the canonical example.

26 / 43sliding window log
4.3 · Sliding window counter

An estimate from just two numbers

previous window, weighted downcurrent window
3 + 8 × (1 − 5/15) = 8.3
Result: Allowedestimate 8.3 / 10

Drag the sliders to see current + previous × (1 − elapsed / window) respond — a 10-per-15-minute limit, the same shape as the login example. It assumes traffic is spread evenly through each window; a burst concentrated at the edges of two windows can still slip to roughly 2× the limit.

Each key needs only two integers instead of a growing log. O(1) memory, usually within a few percent of exact — the usual production default for public APIs.

27 / 43sliding window counter
4.6 · GCRA

Token bucket, rewritten as an appointment book

// tat = "theoretical arrival time" — one field,
// not {tokens, last_ts}
now  = current_time()
tat  = max(GET(key), now)
allow_at = tat - burst_window

if now >= allow_at:
  SET(key, tat + emission_interval)
  return ALLOWED
else:
  return DENIED, retry_after = allow_at - now
  • Mathematically equivalent to token bucket — same burst allowance, same steady rate — but stores one value instead of two.
  • Used inside redis-cell, a native Redis module that implements this in C.
  • Rarely hand-rolled in application code: token bucket is easier to reason about and just as capable. Worth knowing GCRA exists as "the one-field version."

Generic Cell Rate Algorithm — originally from ATM network traffic control, repurposed for API rate limiting. The name is the least intuitive part; the mechanism is a direct restatement of token bucket.

Where the rate-limit service sits

32 / 43system design · architecture
5.3 · Redis Cluster sharding

Per-user keys hash naturally; global keys don't

// per-user: one natural key, one node
rl:{user_456}:token
// hash "user_456" → 1 fixed slot → 1 fixed node
// Lua script stays legal, no CROSSSLOT

// global per-endpoint: no natural entity key,
// so split across N shards instead
rl:global:{/api/send}:shard:{random(0,15)}
// 16 shards, each budgeted at
// total_limit / 16 × 1.1   (10% buffer)

A per-user limit has a natural key and hashes to one node cleanly. A global, per-endpoint limit has no such entity — sharding it across 16 keys spreads the writes instead of hammering one hot key, trading a small amount of precision (the buffer) for throughput.

The buffer exists because 16 independently-checked shards can each individually allow a request right at their own edge, letting the true global total run slightly over — accepted on purpose.

33 / 43sharding · per-user vs. global
5.4 · Hard limit vs. soft limit

Same check, a different response to the result

Hard limit
Crossing it rejects immediately

Free tier: 100 req/min, no exceptions. Behavior: an instant 429. Used for security and preventing abuse — there's no negotiating with it.

Soft limit
Crossing it warns, but keeps serving

Pro tier: 1,000 req/min — cross it and the request still goes through, logged and flagged for an overage charge rather than rejected. Business flexibility, not security.

val result = rateLimiter.check(userId)
when {
  result.count > hardLimit -> return HTTP_429
  result.count > softLimit -> { logger.warn("approaching limit"); proceed() }
  else -> proceed()
}

The same rateLimiter.check() call backs both — what differs is purely what the caller does with the result.

34 / 43hard limit vs. soft limit
5.5 · When Redis itself is down

Fail-open vs. fail-closed

Fail-open
Let every request through

Higher availability, briefly no protection. Most public APIs choose this, paired with a circuit breaker and tight monitoring — an outage in the limiter shouldn't take down the product it was protecting.

Fail-closed
Reject everything

Protects billing and security, drops availability to zero for the duration. Chosen when letting anything unmetered through is worse than an outage — payment and quota enforcement, mostly.

"Most public APIs fail open" is the practical default — the limiter existing to protect availability shouldn't itself become the single point of failure that removes it.

35 / 43fail-open vs. fail-closed
5.6 · Being a good client

Pace before the limit, absorb the 429 after

Retry-After
Read it, then re-enqueue

The response header names the wait, either as seconds or as an HTTP date. Clamp it to a sane range, then put the same job back on the queue with that delay.

Shared circuit gate
One 429 should speak for everyone

A single shared "closed until" timestamp means one rejected call pauses every concurrent caller — instead of each one discovering the limit by being rejected in turn, which is the behavior most likely to get a whole integration blocked outright.

pacer draining evenly, ahead of the limit429 → gate closes for a bounded window

A token-bucket pacer and a reactive circuit gate solve different halves of the same problem: the pacer tries to never get a 429 in the first place, the gate makes sure one 429 isn't wasted as a signal only its own caller sees.

Checkpoint questions

Three questions, easy to hard — a quick way to check the ideas actually landed.

Use these live: ask, pause, then reveal. The hard question is a good one to leave as a take-home if time runs short.

40 / 43act vii · checkpoint questions
Checkpoint questions

Easy, medium, hard

  • easy Which HTTP status code is returned when a rate limit is exceeded?
    → 429 Too Many Requests, with a Retry-After header telling the client how long to wait.
  • medium Why does a Fixed Window Counter let through roughly 2× traffic at a window boundary?
    → Each window resets independently: 100 requests at 12:00:59 fill window 12:00; the clock ticks over, the counter resets to zero, and 100 more immediately after are also allowed — 200 requests in about two seconds against a 100/minute limit. A sliding window never resets abruptly, so it doesn't have this edge.
  • hard A Redis round trip costs ~5ms per check. How does that cap throughput, and how would you optimize it?
    → One thread tops out around 1000ms / 5ms = 200 req/s; 100 concurrent coroutines gets to ~20,000 req/s — not unlimited. In roughly increasing effort: EVALSHA instead of EVAL, a pooled connection, a local cache synced every ~100ms (cuts round trips ~99%, can briefly overshoot), colocating Redis in the same availability zone, and pipelining non-Lua commands where the operation allows it.

The hard question's answer is really a menu, not a single fix — most real systems combine two or three of these rather than picking one.

Takeaways

Five things worth carrying out of this room.

Close on the two roles from the cover: protecting your own system, and behaving as a good client of someone else's.

42 / 43act viii · summary
Takeaways

Five things worth remembering

  • algorithm Token bucket for bursty inbound traffic; leaky bucket when the output rate matters more than the input shape; a counter for everything else. GCRA is token bucket with one field instead of two.
  • correctness Any read-then-write on a shared counter needs an atomic primitive — a Lua script or equivalent — or a crash between the two steps corrupts the count. In a cluster, remember the hash tag.
  • design The key and the response code carry as much risk as the algorithm: never key on caller-supplied data alone, and never let a 429 reveal information a 401 wouldn't.
  • scale Know whether the counter lives per-process or in a shared store — that answer, not the algorithm, decides what the limit actually is once you scale out.
  • backoff Exponential backoff spaces retries apart over time; only jitter spreads concurrent clients apart from each other — and a server-issued Retry-After still needs it.

Close by connecting back to the two roles from slide 1: everything here is either protecting a system from its callers, or being a well-behaved caller of someone else's.
